Case file #01 · Frontend

The data was right. The UI was wrong.

Symptom
State looked correct in DevTools, yet the screen kept showing old data after updates.
Root cause
Stale closures and improper memoization. A memoized callback was holding on to an old snapshot of state.
Fix
Derive values instead of copying them, use functional updates, correct the dependency arrays, and move state to where it’s used.
Rule I keep
Memoize because the profiler says so, never out of habit.
// illustration: a stale closure
useEffect(() => {
  const id = setInterval(() =>
    setCount(count + 1), 1000); // count frozen at 0
  return () => clearInterval(id);
}, []);

// the fix: don't close over stale state
setCount(c => c + 1)

Case file #02 · Architecture

When the browser is the database.

Symptom
The CRM stored everything in each browser’s localStorage. Data couldn’t be shared between users, drifted out of sync, and nothing server-side protected it.
Root cause
The data had no owner. The client was acting as the source of truth for a multi-user product.
Fix
Moved ownership to an Express and MongoDB REST API with server-side validation, and refactored the UI to treat the server as the source of truth.
Rule I keep
Decide who owns the data first. The architecture follows from that.
// before: the browser is the database
const leads = JSON.parse(
  localStorage.getItem('leads') || '[]'
);

// after: the server owns the data
const res = await fetch(
  `${API}/leads?stage=qualified&sort=-updatedAt`
);
const { data } = await res.json();
